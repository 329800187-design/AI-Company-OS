# AI Company OS 原始目标、边界与纵向路线

## 1. 原始目标

AI Company OS 的目标是一个通用的 AI 业务流程执行系统：用户提交业务目标，系统发现当前可用能力，选择主脑，拆解为可验收步骤，调度 Agent 执行，保留过程证据，并在人工确认后交付结果。

它不是电商工具、营销工具、浏览器机器人、单一模型聊天窗口，也不是把本机所有程序无条件接管的自动化脚本。行业、渠道、目标站点和交付格式都必须来自用户输入或显式配置。

## 2. 核心闭环

```text
用户目标
  -> 能力发现
  -> 主脑/API 选择
  -> 任务澄清与拆解
  -> Agent 路由与执行
  -> 结果、日志、证据
  -> 验收与人工确认
  -> 交付物与运行记忆
```

任何一个环节缺失，都只能算演示功能，不能算完成主项目闭环。

### 关键状态

- `discovered`：在允许的扫描范围内被发现。
- `available`：健康检查通过，具备运行条件。
- `enabled`：用户明确允许进入调度池。
- `runnable`：系统有对应适配器，能够实际执行，而不是只有名称或版本号。
- `verified`：执行结果经过规则或人工验收，形成可追溯证据。

只有 `available + enabled + runnable` 的 Agent 才能进入任务路由。发现到的外部 CLI 目前默认关闭，并且需要专用适配器后才进入实际执行池，不能因为命令存在就伪装成已接入。

## 3. 系统结构

### 表现层

- `Boss / Commander`：目标输入、计划、执行进度、验收和交付。
- `Settings`：Provider、API Key、Base URL、Model、主脑状态和连接测试。
- `Agent Console`：本机能力发现、启用状态、风险、扫描范围和调度资格。
- `Delivery / Memory`：交付物、审计记录和人工确认后的有限运行记忆。

### 编排层

- `BrainManager`：统一主脑选择、运行时配置和对话调用。
- `CEO / Commander`：目标澄清、任务拆解、依赖排序、Agent 调度和结果汇总。
- `AgentRegistry / AgentDiscovery`：扫描、健康检查、启用控制和能力路由。
- `Governance`：目标拦截、风险分类、人工审批和一次性执行约束。

### 执行层

- 项目内置 Agent：代码、系统、研究、数据、网站、图片、视频、沟通和验收等通用能力。
- 本机外部能力：CLI、HTTP 服务、MCP、API Provider；必须有明确的协议和适配器。
- 真实外部连接：默认不启用，必须经过允许主机、凭据、审批和审计配置。

### 数据层

- 任务、步骤、状态、依赖、执行结果和错误。
- 交付物及其元数据。
- 脱敏审计事件。
- 只保存人工接受后的结构化运行经验，不把原始密钥、完整网页内容或任意本机文件写入记忆。

## 4. 主线边界

### 属于主线

1. 通用目标到计划的拆解质量。
2. 本机能力的可观察发现与真实可调度性。
3. Provider/API Key/Model/Base URL 的运行时统一配置。
4. Agent 的能力路由、依赖注入、执行结果和验收。
5. 高风险操作的审批、执行、回执和审计。
6. 交付物、历史和人工反馈形成有限的改进闭环。

### 不属于当前主线

- 针对某个行业、平台或渠道继续增加专用页面。
- 无适配器地接入更多 CLI 名称或模型名称。
- 默认递归扫描整块硬盘、读取隐私文件或搜集所有凭据。
- 浏览器自动化的具体公司业务流程。它是可选执行能力，不改变主项目定位。
- 在没有真实 Provider 的情况下生成“AI 已完成”的假结果。

## 5. 扫描与安全边界

本机能力发现采用“可解释、有限范围、用户可控”原则：

- 扫描项目内 `agents` 和 `agents/installed` 的清单与入口。
- 检查 PATH 中声明的已知 CLI 命令版本。
- 检查固定端口上的已知本地服务。
- 检查用户级和项目级 MCP 配置文件。
- 读取 Provider 是否配置的状态，但不在 API/UI 返回密钥明文。

默认不做全盘递归扫描，不读取密码库、浏览器 Cookie、SSH 私钥、任意隐藏目录或未声明的外部账号。若未来需要扩大范围，必须增加显式扫描范围、权限说明、排除规则、超时限制和审计记录。

### 高风险操作必须经过

```text
提出计划 -> 人工确认 -> 预检 -> 一次执行 -> 回执 -> 人工验收
```

浏览器表单提交、外部写入、命令执行、文件删除、账号操作和部署都属于高风险或可升级风险动作。目标主机必须显式配置并通过 allowlist 校验；令牌只能从受保护配置读取，不能放进任务内容、日志或交付物。

## 6. 当前阶段

当前工作区已经具备通用业务流程、Boss/Commander、Agent Registry、交付中心、运行记忆和治理基础。本轮修正的重点是把能力中心从“展示扫描结果”推进到“配置统一、真实状态、可调度边界清晰”：

- Provider 状态支持运行时读取和保存。
- Chat、Commander、CEO 共享同一个当前主脑。
- Settings 支持 Provider、密钥、Model、Base URL、连接测试和错误反馈。
- Agent Discovery 展示扫描范围；Registry 只把可用且已启用的 Agent 放入路由。
- 项目内置研究、网站等 manifest Agent 纳入调度。
- 外部 CLI 仍需专用执行适配器和审批后才能成为真正的执行 Agent。

## 7. 下一步纵向路线

### 7.1 当前下一步：能力闭环验收

- 用真实页面验证 Provider 保存、切换、连接测试和 Chat 实际使用的主脑一致。
- 用真实本机 Agent 验证目标拆解、步骤分配、依赖执行和验收结果。
- 为每个可调度 Agent 补齐 `runnable`/适配器状态，避免“发现即能执行”的误解。

### 7.2 随后：单一可验收任务链

选择一个通用、低风险的本地目标，完成“目标 -> 计划 -> 人工确认 -> 执行 -> 验收 -> 交付”全链路；不同时扩展新的业务页面。

### 7.3 再后：受控外部能力

仅在本地链路稳定后，逐个接入 CLI、MCP、浏览器或外部 API，并为每种能力提供适配器、权限、审批和回执测试。

## 8. 完成标准

主项目达到阶段目标的标准不是页面数量，而是：

1. 用户能明确选择并验证当前主脑。
2. 系统能报告本机真实发现范围和可调度 Agent。
3. 目标能被拆为真实可执行步骤，且不会把普通目标伪装成 QA。
4. 每一步都有状态、结果、失败原因和验收边界。
5. 高风险动作不会绕过人工确认。
6. 没有 API Key、适配器或外部权限时，系统明确报告未就绪，而不是返回假成功。
